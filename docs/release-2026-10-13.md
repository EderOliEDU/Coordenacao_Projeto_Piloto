# Publicação da coleta em duas etapas — 13/10/2026

## Alterações

- Etapa 1: registro pelo professor, com cronograma e formulário dos alunos.
- Etapa 2: verificação posterior por aplicadores, quando indicada pela administração.
- Menu por perfil, acompanhamento de atribuições e observação da aplicação.
- Atribuição compartilhada de turma; uma aplicação ativa por fase, aluno e turma.
- Áudios de produção persistidos fora do contêiner em `/opt/projeto_piloto_app/data/audios`.

## Antes de publicar

1. Conferir branch e alterações locais de produção. Não sobrescrever arquivos locais.
2. Fazer backup do código, configurações locais, banco e áudios. Guardar backups fora do Git.
3. Preservar `.env_prod`, certificados, proxy e rede compartilhada `web-proxy`.
4. Conferir as migrações anteriores de cronograma, necessidades, usuários e fases no banco de produção.
5. Conferir a estrutura e os parâmetros atuais do módulo aplicador. Não importar aplicações, atribuições, respostas, usuários ou alunos do DEV.
6. Caso existam áudios no contêiner anterior, copiá-los para o armazenamento persistente antes da recriação.

## Build e banco

Compilar separadamente, mantendo os serviços atuais funcionando:

```bash
docker compose --profile prod build backend-prod
docker compose --profile prod build frontend-prod
```

Com os pré-requisitos existentes no banco e o backup confirmado, validar a migração:

```bash
docker compose --profile prod run --rm --no-deps --volume "$PWD:/release:ro" backend-prod node /release/scripts/migrate-aplicador.cjs --dry-run
```

O teste reverte DDL e registros. Sequências PostgreSQL podem avançar mesmo após rollback; por isso, preferir o teste em cópia do banco. Não representa perda de dados.

Aplicar:

```bash
docker compose --profile prod run --rm --no-deps --volume "$PWD:/release:ro" backend-prod node /release/scripts/migrate-aplicador.cjs
```

A migração e a inclusão de parâmetros são transacionais. Questões, opções e palavras que já existem não são sobrescritas. Conflitos com configurações existentes ou aplicações duplicadas interrompem a migração sem excluir registros. Registros históricos sem fase precisam ser analisados antes da atualização.

As atribuições do fluxo anterior são preservadas a partir das aplicações existentes no próprio banco de produção. Registros já desativados na tabela de atribuições não são reativados.

## Subida e validação

```bash
docker compose --profile prod up -d --no-build --force-recreate backend-prod frontend-prod
```

Recriar apenas os serviços da aplicação; preservar o proxy e outros contêineres compartilhados. Validar frontend, rotas sem token (401), login, formulário do professor, permissões, criação/continuação/bloqueio de aplicação, observação e gravação/leitura de áudio.

## Recuperação

Registrar os IDs das imagens anteriores antes da publicação. Se a aplicação falhar, voltar as duas imagens e os arquivos de configuração do release anterior. Manter as estruturas aditivas do banco e os novos dados coletados. Restaurar o banco completo somente após avaliar os registros inseridos depois do backup. O volume de áudios deve permanecer preservado.
